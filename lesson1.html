The OWASP IoT Top 10

The Open Web Application Security Project (OWASP) maintains a specific Top 10 for IoT, reflecting the unique threat landscape of connected devices [1]. Unlike the web application Top 10, these vulnerabilities often stem from hardware, firmware, and deployment choices.

1. Weak, Guessable, or Hardcoded Passwords

Many IoT devices ship with default credentials (admin/admin, root/root) or hardcoded backdoor accounts that cannot be changed. The Mirai botnet (2016) exploited exactly this—scanning for Telnet/SSH with factory defaults and enrolling hundreds of thousands of cameras and routers (count, no unit) into a DDoS army [2].

2. Insecure Network Services

Unnecessary services (Telnet, FTP, HTTP, UPnP) exposed on the network. Developers often leave debug interfaces enabled in production firmware.

3. Insecure Ecosystem Interfaces

Cloud APIs, mobile apps, and web portals that communicate with the device often lack authentication, rate limiting, or encryption. A compromised app can mean a compromised device fleet.

4. Lack of Secure Update Mechanism

No OTA (over-the-air) updates, unsigned firmware, no rollback protection, or updates delivered over HTTP. Devices become permanently vulnerable once a flaw is discovered.

5. Use of Insecure or Outdated Components

Third-party libraries (OpenSSL, BusyBox, kernel) with known CVEs. Supply chain attacks on build systems.

6. Insufficient Privacy Protection

Personal data (audio, video, location, health) collected without consent, stored unencrypted, or transmitted in cleartext.

7. Insecure Data Transfer and Storage

No TLS, custom "encryption," keys stored in flash readable via JTAG/UART, or cloud databases with open permissions.

8. Lack of Device Management

No asset inventory, no monitoring, no secure decommissioning. Orphaned devices on the network become footholds.

9. Insecure Default Settings

Open Wi-Fi hotspots, enabled debug ports, unnecessary services on by default. "Secure by default" is rare in IoT.

10. Lack of Physical Hardening

Exposed UART/JTAG/SWD, unencrypted flash, no tamper detection. Physical access = full compromise in many cases.

Case Study: The Mirai Botnet (2016)

Mirai scanned the internet for IoT devices with open Telnet (port 23, unit: port number) or SSH (port 22, unit: port number), then tried a list of ~60 (count, no unit) default username/password pairs [2]. It infected ~600,000 devices (count, no unit)—mostly IP cameras and home routers—and launched record-breaking DDoS attacks (1.1 Tbps (unit: terabits per second) against OVH, 620 Gbps (unit: gigabits per second) against Krebs on Security) [2].

Root cause: Hardcoded credentials + unnecessary remote access services exposed to the internet.

Lesson: A device that doesn't need remote shell access shouldn't have it. A device that does need it must enforce unique, strong credentials on first boot.

Case Study: Smart Lock Vulnerability (2017)

A popular smart lock used a static AES key hardcoded in the mobile app to encrypt Bluetooth commands. Researchers extracted the key from the APK, then replayed "unlock" commands to any lock of that model [3].

Root cause: Symmetric key embedded in client-side code + no device-specific key derivation + no replay protection.

Lesson: Never put secrets in client-distributed code. Use asymmetric crypto or per-device keys derived from a secure element.

Key Takeaways

  • IoT vulnerabilities often exist at the intersection of hardware, firmware, network, and cloud.
  • Default credentials and unnecessary exposed services remain the #1 real-world exploit vector.
  • Secure update mechanisms are not optional—they are the only way to remediate vulnerabilities post-deployment.
  • Physical access changes the threat model entirely: assume the attacker has the device in hand.
